- **Reason for new file:** per spec Gherkin Impact: "the repo has no `features/` tree at all and the Auto-Refresh settings journey is user-observable." Closest journey `e2e/appearance.spec.ts` covers the client-only theme choice, a different journey.

## Tests Written

### `e2e/settings-auto-refresh.spec.ts`

- **"HP-1: Manual is the default and shows no schedule controls"**: radios Manual/Interval/Daily in order, Manual `aria-checked=true`, copy "Only when you tap refresh.", zero interval buttons, no time input, no cost hint.
- **"HP-2: ... (30 min | 1 hour | 2 hours | 4 hours | 6 hours)"**: Interval checked, all 5 options visible, clicked option `aria-pressed=true` and all others `false`, exact description "Every <option> while your computer is on.", cost hint visible.
- **"HP-3: Daily mode shows a labelled time input prefilled with 07:00"**: Daily checked, `getByLabel('Every day at')` is `type=time` with value `07:00`, exact catch-up copy, cost hint, no interval buttons.
- **"HP-4: Daily time survives save and reload"**: fills `07:30`, clicks Save Preferences, asserts PUT 200 and response body `refreshMode: 'daily'`, `refreshDailyTime: '07:30'`, button shows "Saved"; after reload Daily checked, value `07:30`, copy updated.

Design notes: the file runs `serial` because HP-4 writes the single preferences row and HP-1 asserts the default. `afterAll` resets `refreshMode: manual` via `PUT /api/preferences` so other files see the default. All locators scoped to the Auto-Refresh section. No `fs` / source inspection.

## Implementation Issues Found

None blocking. All acceptance criteria verified. Observations for review:

### Scheduler backoff state is module-scoped, the start guard is global

- **Expected (from spec):** tick registers once per process (`globalThis` guard). Backoff is in-memory.
- **Actual:** `__smartbriefSchedulerStarted` is on `globalThis`, but `tickRunning` and `lastFailureAt` are module-level `let`s in `src/lib/scheduler.ts`. After a dev hot reload the old timer keeps calling the old module instance, so behaviour is consistent; a newly loaded module copy is not wired to any timer. No functional defect in `next start`.
- **Evidence:** code read of `src/lib/scheduler.ts`.
- **Severity:** minor

### Clearing the Daily time gives a generic save error

- **Expected:** not specified.
- **Actual:** empty time sends `''`, PUT returns 400, page shows the generic "Failed to save" (already listed by impl).
- **Severity:** minor
